A model scores 92% on your benchmark. Is it good at the task, or has it seen the answers? For any eval built from public material, you increasingly can't tell. **Contamination** is when evaluation data, or something close to it, appears in training data. It turns a test of capability into a test of memory.

## How contamination happens

It's rarely deliberate. It's a side effect of training on enormous web crawls.

- **The benchmark itself is published.** Once a dataset is on GitHub or Hugging Face, it gets scraped, mirrored, and quoted in blog posts and papers.
- **Solutions get discussed.** Even if the test set is withheld, people post solutions, walkthroughs and "how I got X% on Y" write-ups.
- **The source material is public.** A task built from a well-known open-source bug, a textbook exercise, or a popular interview question was in the crawl before you wrote it.
- **Paraphrases slip through.** Exact-match filtering catches copy-paste. It misses translations, reformatted versions and lightly edited variants.
- **Evals become training targets.** Once a benchmark matters, people optimize for it, sometimes by training on similar data. The line between "similar" and "the same" blurs.

The result: scores on public benchmarks drift upward over time in ways that don't fully reflect capability gains.

## Detecting it

No single test is conclusive, so use several.

**N-gram overlap.** Search the training corpus, if you have access, for long n-gram matches with eval items. Cheap and useful, but blind to paraphrase.

**Completion probes.** Give the model the first half of an eval item, such as a problem statement or the start of a code file, and see whether it reproduces the rest verbatim. Exact reproduction of an unusual string is strong evidence of memorization.

**Perturbation drops.** Make the task semantically identical but superficially different: rename variables, change numbers, reorder clauses, swap the domain. A model that actually reasons should score about the same. A large drop on perturbed versions points to memorization of the original.

```text
original:   "A train leaves station A at 3pm going 60 km/h..."   -> 94% correct
perturbed:  "A ferry leaves port Q at 11am going 45 km/h..."     -> 61% correct
            same structure, new surface        -> the gap is the warning sign
```

**Time-split evaluation.** Compare performance on problems created *before* the model's training cutoff against problems created *after*. Contest-based coding benchmarks that keep adding new problems use this approach. A sharp drop on post-cutoff problems is hard to explain any other way.

**Canary strings.** Embed a unique random string in your eval files and ask the model to complete it. If it can, your data was in training. This only works if you add the canary *before* the data leaks.

## Preventing it

Detection tells you a benchmark is compromised. Prevention keeps it useful.

### Author from scratch

The most robust defense is tasks that never existed publicly. Write them fresh, from domain expertise, not by adapting existing problems. A task inspired by a real bug is fine if you rebuild the scenario. A task copied from a public issue tracker is already contaminated. This is a big part of why **human-authored** tasks from experts are valuable: they're new to the model by construction.

### Keep the test set private

Publish a small sample so people can understand the format. Keep the scored set behind an API or under access control. Don't commit it to public repos, don't paste it into public chat tools, and don't include it in papers verbatim.

### Parameterize where possible

For tasks with structure, write a generator, not a fixed instance. A template with randomized numbers, names, and configurations can produce fresh variants at eval time. The model can't memorize a problem that didn't exist until you ran the eval.

### Rotate and retire

Treat every eval set as having a shelf life. Track scores over time, run perturbation checks each release, and retire items that show memorization signals. Replace them with newly authored ones.

### Check your own pipeline

Contamination isn't only a pretraining problem. If you fine-tune on data that was generated by a model that saw your eval, or on synthetic data seeded from eval items, you've contaminated it yourself. Keep strict separation: eval items never feed any data-generation process.

## What a clean result looks like

An eval you can trust usually has:

```text
[ ] items authored after the target model's training cutoff, or never public
[ ] no large perturbation drop: renamed / re-numbered variants score similarly
[ ] no verbatim completion when probed with item prefixes
[ ] a private scored set, a public sample for documentation only
[ ] a rotation plan, and a log of when each item was added
```

## Why this matters more every year

As models train on more of the internet, the set of "things the model hasn't seen" shrinks. Public text has mostly been read. New, expert-written material that was never posted publicly becomes the scarce resource, both for measuring models honestly and for teaching them something new.

The same principle runs through hard-task authoring generally ([writing tasks models fail at](/blog/writing-tasks-frontier-models-fail)) and calibration ([the 10–30% band](/blog/the-10-30-band-calibrating-task-difficulty)): **a task is only informative if it tests something the model has to work out rather than remember.**
